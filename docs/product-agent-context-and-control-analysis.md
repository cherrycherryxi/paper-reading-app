# 产品 Agent：动态上下文管理与可控性分析

> 分析日期：2026-08-01  
> 范围：仅讨论面向用户的「探讨」产品 Agent；不将 OpenWolf/Codex 的开发协作记忆当作产品能力。

## 结论摘要

产品 Agent 已具备「有界上下文、自动摘要、外置动作状态、人工确认、可观测性」等关键基础，整体适合继续迭代。

当前最明确的产品缺口是**面向用户的显式长期记忆**：系统能保存聊天历史和业务数据，但不会把用户确认过的偏好、稳定观点、持续目标或待办提炼为可管理、可检索、可删除的独立记忆。

在安全与稳定性方面，优先补强 MCP 工具调用的超时、幂等、重试策略和跨链路追踪；多 Agent 信任边界可等到实际引入多个独立 Agent 后再建设。

---

## 一、动态上下文管理

### 1. 滑动窗口：已实现

每个聊天上下文按书籍、摘抄或全局维度隔离保存为 `chatHistories`。每次模型回复完成后，服务端只保留末尾 40 条消息；因此异常情况下历史也不会无限增长。

- 实现：`app_server.py` 的聊天保存逻辑，`history = [...][-40:]`。
- 结果：不同书籍/摘抄不会混用上下文，单个上下文有明确上限。

### 2. 摘要压缩：已实现

当单个历史超过 10 条消息，系统会保留最近 6 条原文，将更早内容交给模型压成 200 字内摘要，并以「对话历史摘要」作为一条消息持久化。

- 实现：`app_server.py:2535-2564` 的 `compress_chat_history_if_needed()`。
- 调用时机：普通聊天与流式聊天在构造模型 prompt 前都会调用该函数。
- 兜底：摘要模型调用失败时不丢历史，仍按 40 条滑动窗口限制保存。

### 3. 显式记忆：产品内尚未实现

目前产品有三类可持久化信息：

- 业务状态：书、摘抄、阅读记录、关联等，保存在 `user_state.state_json`。
- 聊天状态：`chatHistories` 与 `chatContexts`。
- 对话摘要：作为聊天历史中的一条摘要消息。

这些都不是独立的用户长期记忆库。当前不存在「记忆」实体、记忆来源与置信度、检索策略、用户确认/编辑/删除界面，也没有独立的 Memory MCP Server。

已在 [signals](../optimization/signals.md) 中记录产品信号：将用户明确确认的阅读偏好、稳定观点、持续目标与待办提取为可查看、可编辑、可删除的记忆，并在后续对话按需召回。

> 说明：项目开发体系中的 `.wolf/cerebrum.md`、`.wolf/buglog.json`、`.wolf/memory.md` 属于开发 Agent 的外部知识管理，不等于用户面对的产品记忆功能。

### 4. 任务状态外化：已实现

产品 Agent 的动作不依赖模型上下文“记住做到哪一步”。动作会持久化到 SQLite 的 `agent_actions`，并由状态机管理：

```text
GENERATED → PENDING → APPROVED / REJECTED → EXECUTED / FAILED
```

- 实现：`app_server.py` 的 `agent_actions` 表、`ActionStateMachine` 与 `agent_traces`。
- 结果：刷新页面、模型重试或后端异常后，动作状态仍可恢复和审计；失败动作也可以重新审批后重试。

|---|---|---|---|
| 结构化输出 | 部分具备 | `ResponseParser` 解析 `reply + actions`，支持 Markdown 清理和降级恢复；`ActionValidator` 再按工具 Schema 校验。 | 改用模型 API 级 JSON Schema / structured output；降级解析时只展示文本，不执行任何未被完整验证的动作。 |
| Guardrails | 较完善 | 有鉴权、请求体大小限制、输入长度/重复内容校验、书/摘抄归属校验、动作参数校验、动作数量上限、状态清洗与 AI 限流。 | 增加提示注入防护，以及按工具、实体、上下文定义的细粒度权限策略。 |

## 三、优先级建议

### P0：MCP 工具调用稳定性

**存在的问题**：MCP Dispatcher 目前会把失败返回给上层，但没有独立的调用超时、重试、熔断和幂等控制。网络抖动或服务重启时，重试策略若处理不当可能造成重复写入。

**目标**：让工具调用在瞬时故障下可恢复，在持续故障下快速失败且不重复改写用户数据。

**实现方向**：为调用加 deadline；为每个动作生成 idempotency key；仅对安全操作进行带退避的有限重试；连续失败时进入短暂熔断；将各阶段耗时与结果写入 trace。

**最终效果**：用户看到清晰的可重试失败反馈，系统不因重复请求产生重复笔记、重复加书或重复关联。

### P1：硬化结构化输出与 Guardrails

**存在的问题**：目前可容错解析模型的“近似 JSON”，对体验友好，但不能替代模型 API 层面的结构约束。

**目标**：确保任何会写入用户数据的动作都符合完整 Schema 与权限约束。

**实现方向**：使用 provider 支持的 structured output；保留现有 `ActionValidator` 作为第二道防线；将降级解析限制为纯文本回复；补充针对提示注入的策略测试。

**最终效果**：模型格式异常、恶意文本或上下文污染不会绕过动作校验。

### P2：面向用户的显式长期记忆

**存在的问题**：产品不能稳定记住用户跨聊天、跨书籍持续表达的偏好、阅读目标和待办。

**目标**：在尊重用户控制权和隐私的前提下，让 Agent 能在合适的后续对话中使用这些长期信息。

**实现方向**：新增独立记忆数据模型，至少包含内容、类别、来源、置信度、创建/更新日期、是否经用户确认；提供记忆管理页；仅在相关问题中检索少量记忆并纳入 prompt；支持编辑、删除、导出和关闭记忆功能。

**最终效果**：用户能看见、纠正和删除 Agent 记住的内容，Agent 也不再只依赖短期对话摘要。

### P3：可观测性深化

**存在的问题**：已有日志、trace 和 Dashboard，但一次用户操作在前端、模型与 MCP 之间还缺少统一关联，系统也缺少面向运营的异常阈值。

**目标**：能快速回答“哪一步失败、影响多少用户、是否需要处理”。

**实现方向**：贯穿 `traceId`；增加工具调用结果指标；配置错误率/超时率告警；为关键链路定义 SLO。

**最终效果**：线上问题从手工翻日志转为可定位、可预警、可量化。

### 暂不优先：Multi-Agent 信任边界

当前产品尚未运行多个独立 Agent。过早建设 A2A 授权体系会增加复杂度，而暂时没有对应收益。应在引入独立记忆、检索或规划 Agent 时再同步设计其身份、授权与审计边界。

## 四、现有能力的定位

当前架构的优势是：所有会影响用户数据的 Agent 动作都有“解析 → Schema 校验 → 持久化 Pending → 用户确认 → 工具执行 → Trace”的闭环。它比“模型直接写数据库”的模式更可控。

下一阶段不需要推翻这一闭环；应在其上补齐两层能力：

1. **可靠性层**：让外部模型和 MCP 工具的失败可预测、可恢复、可观测。
2. **长期个性化层**：让用户拥有并管理 Agent 的长期记忆，而非把记忆藏在不可见的聊天记录中。
