## 5. 速度/质量平衡规则

1. **双轨制**:功能轨(白天,你主导)允许「粗糙先用」——UI 类可以不写测试,真机用一周再补;修缮轨(夜间 agent)维持现状的强测试纪律。
2. **质量闸门分级**:涉及**数据安全**(import/export、state 写入、DB schema、OCR 落盘)= 必须测试 + 真机双验,无例外(bug-274 的教训);纯 UI/文案 = 真机即可,test-on-regression。
3. **修缮预算阀**:夜间 implement agent 每周 ≤ 8 个 PR(**2026-07-18 由 4 上调至 8**:owner 进入面试/刷题备考期,项目需夜间轨自主推进;Agent2 每晚至多 1 项、周天花板本就 ~7,故 8 ≈ 解除节流、几乎每晚开一个,晨间轨照旧审+闸门合入 dev,prod 仍手动);explore 蓄水池只进不出会无限膨胀(6/12 时 69 条 → **7/04 已 148 条,承诺的每月 prune 一次未执行**),下次 prune 定在 W28 内:90 天无人提拔的条目归档,与已合并 PR 重复覆盖的条目标 stale。**(2026-07-06 已执行:explore.md 156 → 113 活跃,归档 43 条已被合并 PR 修掉/⛔排除的条目至文件末尾『## 已归档』;>90 天年龄标准命中 0——蓄水池最早条目仅 2026-05-30,故年龄杠杆本轮不适用;保守起见,未修的重复条目一律留在活跃区,故未压到 <80 目标。)**
4. **北极星税**:今后每个新 OPT 登记时多写一行 `northstar: <对北极星的贡献,一句话>`,写不出来自动 P3。这是防「工程上正确但产品上无谓」的最便宜机制。
5. **止损规则**:任何功能真机用 2 周后 signals 里零正反馈 → 下个周一仪式上讨论砍掉,沉没成本不进决策。
6. **计划外让位显式化(2026-07-04 加,W27 教训)**:计划外工作(线上事故、owner 临时高价值需求)可以合法挤掉周焦点,但必须在发生当周的归档/备忘里写一句「本周焦点让位于 X」——让取舍被看见并在下个周一重新确认焦点,而不是让焦点静默滚动数周(W27 四项拖三周即此病)。
7. **焦点落盘前先验证「执行轨还活着」(2026-09-14 加,W36/W37/W38 教训)**:周一仪式在把事项指派给某条轨(夜间 agent / 晨间轨)之前,必须先确认该轨上周**真的产出过提交或日志**;若某轨已静默,对应事项要么改派给仍在运行的轨,要么在焦点里显式写明「前置条件是恢复该轨」,不得把事项指派给一条空转的轨再宣称本周有计划。同理,仪式自身的产出(摘要长度校验等)连续失败两次以上必须当周升级为显式故障记录,不能让 roadmap 静默停在三周前的焦点上——**「焦点在文件里没有更新」本身就是必须被记录的信号**(W36/W37 两次仪式均因摘要校验中止,文件却看不出任何异常)。

8. **「已合入 dev」≠「用户已获得」（2026-09-28 加,W40 教训）**:prod 是 `main` 指针,只能靠 `ALLOW_MAIN_PUSH=1 git push origin feature/agent:main` 快进,而这一步是**手动**的、没有任何定时轨替它兜底。后果:9/06 合入的 OPT-183(采集主路径的 toast 真话性修复)在 dev 躺了 **22 天**,而 owner 每天在用的 prod 一直没有它——同期的 `git diff origin/main feature/agent` 只剩这一处 7+/2-,即「修复早已写完、只是没送到」。**规则**:① 每周一仪式把 `git rev-list --count origin/main..origin/feature/agent` 与 `git diff --stat origin/main origin/feature/agent` 当作固定检查项写进焦点节;② 凡影响**每日主路径**的已合入修复,当周必须发版,不得跨周积压;③ 「已修好」这句话在本路线图里默认指**prod 生效**,只合入 dev 的要显式写「未发布」。
